# LLM-backed engineering collaboration

Network, Windows, Linux, CloudOps, DevOps and Security twins use the configured local Ollama model for bounded incident reasoning. They are role-scoped model invocations inside the application, not separately trained models or independently deployed services. The existing `CLOUDOPS_DEVOPS` persona remains a compatibility alias for old diagnostic records.

The incident workflow records an `AgentInvestigationRequested` message, sends it through the authenticated gRPC evidence exchange, collects allowlisted diagnostics, and invokes the receiving role's reasoning prompt. A correlated `AgentValidationReplied` message returns observations, missing evidence and a next check to the owner. The owner receives prior replies and produces `AgentOwnerAssessmentCompleted`. These records survive restart in the incident ledger. This is the application's internal A2A workflow, not an implementation of the external A2A interoperability standard.

ServiceNow's incident description, assignment group and `caused_by` change reference are retained as reported context. They are never proof of causation. For a Network issue after Windows maintenance, a Windows diagnostic can use a different CI only when exactly one persisted Windows incident shares the same change reference. Otherwise the Windows twin reports missing target evidence. Multiple matching targets require disambiguation; no host is guessed. Change records already in the aggregate are available to reasoning. Reading a referenced ServiceNow change's full history requires a change-record connector; this implementation does not fetch that table.

Automatic routing runs for new or materially updated unresolved ServiceNow incidents when live read ingestion is configured (`TELEMETRY_MODE=LIVE`, `SERVICENOW_INCIDENT_INGEST_ENABLED=true`, `AGENT_COLLABORATION_ENABLED` not false). Local deployment remains simulation. Open a ServiceNow incident and use **Ask twins to investigate** to exercise the workflow locally; **Refresh exchanges** displays persisted conversations. Existing exact workflow binding, role checks, approval controls and work-note publication settings apply.

A transport acknowledgment is not a validation reply. `OBSERVATIONS_AVAILABLE` means successful diagnostic observations exist, not that the hypothesis is confirmed. `SIMULATED` and `NEEDS_EVIDENCE` cannot be upgraded by the LLM. Generated assessments are explicitly unverified, and unsupported evidence IDs are rejected. Model timeout or invalid JSON retains a deterministic evidence report. Every round is bounded to one request/reply per participating role plus an owner assessment. The model has no direct execution capability.

CloudOps currently interprets incident/change context but has no generic cloud diagnostic template. DevOps requires a Kubernetes namespace. Linux uses an allowlisted failed-service check. Live command adapters must independently authorize the target and support these templates; the shipped proxy makes no real device connections.

Validation: `npm run lint`, `npm run test:engineering`, `npm run test:cyber`. Regression coverage includes Network-to-Windows maintenance validation on the correct CI, missing-target abstention, forged citations, simulated receipts, authenticated protobuf exchanges and restart persistence. Role guidance and organizational runbooks improve inference context; they are not model-weight training and cannot guarantee every incoming request is understood correctly.
